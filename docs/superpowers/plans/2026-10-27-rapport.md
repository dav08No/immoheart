# Archiv und Jahresrapport — Implementation Plan

> **For agentic workers:** Umsetzung Task für Task mit Subagent-Driven Development (Implementer → Review → Fix-Runden). Steps nutzen Checkbox-Syntax.

**Goal:** Treffer, Objekte und Anfragen werden archiviert statt gelöscht. Eine Archiv-Seite erlaubt Wiederherstellen und endgültiges Löschen. Ein Knopf erzeugt einen Jahresrapport (letzte 12 Monate) als eine Excel-Datei mit Übersicht, echten Excel-Diagrammen, KI-Zusammenfassung und Datenblättern.

**Architecture:**
- Sicherheitsnetz in Postgres: ein Archiv-Trigger auf `matches` und Archiv-Spalten auf `objekte`/`anfragen`. Atomare Funktionen für Archivieren, Wiederherstellen und endgültiges Löschen.
- Next.js sammelt die Rapportdaten (inkl. Archiv), berechnet die Kennzahlen mit reinen, getesteten Funktionen und lässt Gemini nur aus Aggregaten einen Text schreiben.
- Eine einzelne Vercel-Python-Funktion (openpyxl) baut daraus die `.xlsx`. Sie hat keinen DB-Zugriff und ist mit einem Schlüssel geschützt.

**Tech Stack:** Next.js 15.5, React 19, Supabase, Gemini, Vitest; Python 3.12 + openpyxl (Vercel Python Runtime) + pytest.

**Spec:** `docs/superpowers/specs/2026-10-27-rapport-design.md`

## Global Constraints

- Migrationen sind **nur additiv**, weil Preview und Produktion sich eine DB teilen. Der Lösch-Sperr-Trigger auf `objekte`/`anfragen` kommt erst **nach** dem Produktions-Deploy (Task 10, Migration „F2“).
- Migrationen wendet nur der Controller über Supabase MCP an (Projekt `rvxlvrrpltmuzuomdwdf`). Implementer schreiben und committen die Datei und melden dann `NEEDS_CONTEXT`.
- Neue Funktionen:
  - `security invoker` und `set search_path = public, pg_temp`;
  - `revoke execute … from public, anon` und `grant … to authenticated`.
  - Ausnahme ist der Archiv-Trigger: er ist `security definer`, damit er in `treffer_archiv` schreiben darf. RLS lässt dort nur Lesen zu.
- Endgültiges Löschen dürfen nur Konten mit `darf_nutzer_anlegen`. Das wird in der Server Action **und** in der DB-Funktion geprüft. Nur archivierte Daten lassen sich löschen. Es wird kein Protokoll geführt.
- IDs mit `idSchema` (`z.guid()`) prüfen.
- KI:
  - Gemini bekommt **nur Aggregate**, keine Namen, E-Mails oder Texte.
  - Ein KI-Fehler bricht den Rapport nicht ab.
  - Pro Rapport genau ein Gemini-Aufruf.
- Excel enthält keine E-Mail-Adressen, keine Eigentümer-Kontakte und keine Mailtexte.
- Python-Funktion:
  - Header `x-rapport-schluessel`, geprüft mit `hmac.compare_digest` gegen die Env-Variable `RAPPORT_SCHLUESSEL`.
  - Eingabe höchstens 5 MB.
  - Keine Datenteile in Fehlerantworten.
  - Versionen in `requirements.txt` gepinnt.
- UI:
  - nur Bausteine aus `components/ui/*`;
  - `text-ink-2` für Hilfstexte;
  - Primäraktion rechts (R3);
  - ab 360 px nutzbar.
- Code:
  - kein `any`;
  - Dateien unter 200 Zeilen;
  - kurze deutsche Warum-Kommentare.
- Checks:
  - `npm run lint && npx tsc --noEmit && npx vitest run && npm run build`, Fehler sichtbar;
  - Python zusätzlich `python -m pytest api/tests`.
- Commits enden mit Leerzeile und `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Branch `feature/rapport`, Worktree `.worktrees/rapport`. Blockierte Befehle als BLOCKED melden.

## Review Focus

1. **Kein Datenverlust beim Entfernen von Treffern:**
   - Jeder Pfad, der heute `matches` löscht, landet in `treffer_archiv`, und zwar mit dem richtigen Grund.
   - Ausnahme ist das endgültige Löschen (`immoheart.endgueltig`).
   - Test: Zeilenzahl in `treffer_archiv` vor und nach jedem Pfad.
2. **Archivierte Daten sind überall sonst unsichtbar.** Das betrifft:
   - Listen, Zähler, Puls und Matches;
   - die Treffersuche in beiden Richtungen;
   - die Website (`objekte_oeffentlich`);
   - Postfach-Zuordnung (Eigentümer, Absender) und Kennzahlen.
   Die Grep-Liste der Abfragen steht in Task 3.
3. **Endgültiges Löschen:**
   - Nur archivierte Daten und nur für Admins.
   - Atomar, mit Fotos im Storage danach.
   - Ohne Admin-Recht kommt eine Fehlermeldung, und es wird nichts gelöscht.
4. **Rapport-Zahlen stimmen mit der Seite „Zahlen“ überein,** gleicher Zeitraum und gleiche Definition. Leere Zeiträume ergeben eine gültige Datei mit Nullen.
5. **Python-Funktion:**
   - Ohne oder mit falschem Schlüssel: 401.
   - Kaputtes JSON: 400.
   - Eingabe über 5 MB: 413.
   - Grosse, aber gültige Daten (z. B. 5000 Treffer) laufen unter 30 s.

### Task 2: Migration F1 — Archiv-Schema und Funktionen

- [ ] Tabelle `treffer_archiv`:

  - Indizes auf `archiviert_am`, `anfrage_id`, `objekt_id`.

- [ ] Trigger-Funktion `archiviere_treffer()`:

  - Bei `current_setting('immoheart.endgueltig', true) = '1'` nichts tun.
  - Sonst `insert into treffer_archiv` mit `grund = coalesce(nullif(current_setting('immoheart.archiv_grund', true), ''), 'unbekannt')`.
  - Gibt `old` zurück.
- [ ] `objekte` und `anfragen` bekommen die Spalten `archiviert_am timestamptz`, `archiv_grund text` und einen Index auf `archiviert_am`.
- [ ] `create or replace view objekte_oeffentlich`, gleiche Spalten und Grants wie in n5, zusätzlich `and archiviert_am is null`. Die Grants aus `20260927400000_n5_objekte.sql` exakt übernehmen. Die anon-Spalten-Grants auf `objekte` bleiben unverändert, neue Spalten werden nicht an anon gegrantet.
- [ ] `treffer_entfernen(p_ids uuid[], p_grund text) returns void`: setzt `set_config('immoheart.archiv_grund', p_grund, true)`, dann `delete from matches where id = any(p_ids)`.
- [ ] Die Abschluss-Funktionen `treffer_reservieren`, `treffer_vermitteln` und `objekt_nicht_verfuegbar` per `create or replace` mit **identischem** Rumpf aus Migration B, plus `perform set_config('immoheart.archiv_grund', '<Grund>', true)` vor jedem `delete`.
  - Gründe: „Objekt reserviert“, „Anfrage vermittelt“ (bei vermitteln für beide Löschungen), „Objekt nicht mehr verfügbar“.
  - `objekt_wieder_verfuegbar` aus Migration D bleibt, sie löscht nicht.
- [ ] `objekt_archivieren(p_id uuid, p_grund text)`:
  - sperrt das Objekt;
  - Fehler, wenn schon archiviert, oder wenn Treffer mit Status `gesendet`/`reserviert` existieren („Zuerst Angebote abschliessen (z. B. ‚Nicht mehr verfügbar‘).“);
  - setzt den Grund „Objekt archiviert“ und löscht `neu`-Treffer;
  - setzt `archiviert_am = now()` und `archiv_grund = nullif(trim(p_grund), '')`.
- [ ] `anfrage_archivieren(p_id uuid, p_grund text)`:
  - Fehler bei `reserviert`-Treffern;
  - `gesendet` wird zu `erledigt`;
  - Grund „Anfrage archiviert“, `neu` löschen;
  - Archiv-Spalten setzen.
- [ ] `objekt_wiederherstellen(p_id)` / `anfrage_wiederherstellen(p_id)`: Fehler, wenn nicht archiviert; sonst `archiviert_am = null`, `archiv_grund = null`. Das Rematching macht die App.
- [ ] Endgültiges Löschen:
  - `ist_admin()` als SQL-Hilfsfunktion: `security definer`, liest `profiles.darf_nutzer_anlegen and aktiv` für `auth.uid()`; grant nur an authenticated.
  - `archiv_eintrag_loeschen(p_id)`: Admin-Prüfung, dann `delete from treffer_archiv where id = p_id`. Läuft als `security definer`, weil RLS dort kein Delete erlaubt; Admin-Prüfung zuerst.
  - `objekt_endgueltig_loeschen(p_id) returns table(foto_pfade text[])`:
    - Admin-Prüfung, dann muss das Objekt archiviert sein;
    - `set_config('immoheart.endgueltig','1',true)`;
    - Fotopfade sammeln;
    - `delete from treffer_archiv where objekt_id = p_id`;
    - `delete from objekte where id = p_id` (Kaskade auf matches und objekt_fotos);
    - Fotopfade zurückgeben.
  - `anfrage_endgueltig_loeschen(p_id)`: analog, ohne Fotos.
- [ ] `anfrage_rollback(p_id)`: nur Anfragen ohne Nachrichten, die höchstens 10 Minuten alt sind. Setzt `immoheart.rollback='1'` und `immoheart.archiv_grund='Rollback Dublette'`, dann löscht sie.
- [ ] Commit, `NEEDS_CONTEXT „Migration F1 bereit“`. Der Controller wendet sie an, prüft Advisors und regeneriert die Typen; danach Checks und Commit `feat(archiv): Schema, Archiv-Trigger und Funktionen`.
